> 说明：本报告整理自 2026-09-24 的代码审查记录与 E:\模型 实测评估材料。文中全部「路径:行号」证据、复现步骤与实测数据（rtf、报错原文等）均原样保留自该材料；标注「原发现实测/复现」与「本次复核抽查证实」分别为材料中首轮审查与复核两轮工作的结论，本报告为整理成文，未重新执行这些验证。

## 一、项目结构与实现概览

单宿主进程 `host_server.py` 起三个 HTTP 面：

- **8790**（仅环回）：pywebview 壳加载 `ui/` 并提供 `/api/*` JSON API，纯 stdlib http.server；
- **8791**：局域网头显白名单接口；
- **8756**：按需拉起的字幕服务子进程（`vendor/subtitle`，uvicorn/FastAPI）。

DLNA 不另起进程：同进程 import `vendor/dlna` 的 DlnaApp+SSDPServer（默认 8899）。

关键数据流：

1. **音频**——头显/手机采集 PCM 后由设备直接 POST 到 `PC:8756 /transcribe`（或 `/transcribe/stream`），不经过宿主；
2. **字幕**——服务端 VAD 切句 → audiocpp（Qwen3-ASR，回环 8081）识别 → translate_engine 翻译（本地 llama-server 8082 / Ollama 11435 / 云端）→ JSON/SSE 回头显；
3. **状态**——前端 1s 轮询 `/api/state`，宿主探测 8756 `/health` 汇总；
4. **设置**——宿主设置存 `data\integrated_settings.json`，字幕配置存 `data\subtitle_config.json`，规则统一在 `user_paths.py`（安装目录、C 盘零写入、历史位置自动迁移）；
5. **模型**——host_server 的 MODELS_CATALOG + `/api/models/download` 双通道断点续传下到 `models\`，两个 .exe 后端按 config 拉起常驻（Job Object 随父回收），空闲 5 分钟自动释放退出。

### 宿主服务（6 条）

#### F01 [高][缺陷] host_server.py:2404-2414（触发入口 ui/app.js:909）— UI 切换识别模型静默清空字幕配置，流式字幕整条失效

**问题**：UI 切换识别模型时 save_subtitle_config 把 asr.audiocpp 段整段替换成 `{model}`，port 等键被静默抹掉并持久化；audiocpp 回退默认 8083 而流式字幕硬编码 8081，流式字幕整条失效且配置数据丢失，界面无法恢复。

**依据**：深合并只对 translate 组（host_server.py:2405-2410），其余组 cfg[group].update(values)（:2411-2412）整体替换子键；app.js:909 发送 `{"asr":{"audiocpp":{"model":val}}}`，:913 保存后立即 restartSubForConfig 用残缺配置重启。本次复核抽查源码证实：合并逻辑、app.js:909 载荷、stream_bridge.py:101 硬编码 `ASR_BASE="http://127.0.0.1:8081"`、audiocpp_backend.py:87 port 缺省 8083 全部属实；原发现另用与 2404-2417 相同合并逻辑跑过复现：出厂 asr.audiocpp 7 键合并后只剩 `{"model":...}`。后果链：8083 上无服务 → /transcribe/stream 连接拒绝，损坏配置写入 `data\subtitle_config.json`。

**修复**：深合并推广到所有组（至少 asr 二层），ASR_BASE 改从配置读 port。

#### F02 [中][缺陷] host_server.py:367-369 — 设置缓存读写无锁，可永久返回旧设置并回滚并发保存

**问题**：load_settings 读写 _SETTINGS_CACHE 不加 _SETTINGS_LOCK，并发未命中时 key/data 两次独立赋值可交错成「key=新 stat、data=旧内容」，此后每次轮询命中错配缓存永久返回旧设置，下一次 save_settings 以此为基底还会把并发保存的字段静默回滚。

**依据**：_SETTINGS_CACHE 写入是两条独立语句（host_server.py:368-369），load_settings 全程不取锁（_SETTINGS_LOCK 只在 save_settings:454 使用）；交错序列：A stat(旧)+读旧内容 → save 落盘 mtime 变 → B stat(新)+读新内容 → B 写 key(新) → A 写 key(旧) → B 写 data(新) → A 写 data(旧) → key=新 stat、data=旧内容。之后每次 load_settings 命中（:331-334）UI 永远显示旧设置；save_settings 以 load_settings() 结果为基底（:455）造成丢更新。

#### F03 [中][缺陷] host_server.py:919-930 — 看门狗 3 秒启动窗口内不核对代数，主动停止被误报为启动失败

**问题**：_watch_subtitle 的 3 秒启动窗口内进程退出路径不核对代数/归属：启动后 3 秒内点「停止」（sub_stop 主动 taskkill），看门狗把主动停止误报成「字幕服务启动失败：子进程退出（code 1）」，状态停在 error 直到下次启动。

**依据**：:920-929 poll 到退出即无条件写 RT.sub_error、置 RT.sub_proc=None、记「启动失败」；同函数后段（:938-943）和 sub_start worker（:873-880）都有 gen/`RT.sub_proc is proc` 归属核对，唯独这条早退路径没有。sub_stop（:1042-1047）先置 sub_proc=None、gen+1 再杀进程，杀掉的正是 watcher 手里的 proc，:924 条件必成立。附带：:928 的 RT.sub_proc=None 若落在新一轮 sub_start 的 Popen 登记（:878）之后会抹掉新句柄（窗口 ≤0.25s，概率低，主要危害是误报错误状态）。

#### F04 [中][缺陷] host_server.py:841-847 — ASR_MODEL 环境变量兜底是死代码，缺省模型路径指向不存在的目录

**问题**：宿主注入的 ASR_MODEL 环境变量兜底是死代码，真正的缺省模型路径指向不存在的 `vendor\audiocpp\models`：配置缺 audiocpp.model 时服务照常就绪、asr_ready=True，但每条转写都因模型不存在失败。

**依据**：host_server.py:841-847 读 config 的 asr.model（模板无此键，实际键是 asr.audiocpp.model）后 `env.setdefault("ASR_MODEL", ...)`，但全仓库无任何代码读 ASR_MODEL（grep 验证，仅 stream_bridge 的同名常量）；audiocpp_backend.py:93-94 缺省是 `self.dir/"models"/"Qwen3-ASR-0.6B"` = `vendor\audiocpp\models\…`，实测 `ls dist-app/vendor/audiocpp` 只有 LICENSE/assets/cpu。「宿主兜底注入模型路径」的设计意图整体落空。

#### F05 [中][缺陷] host_server.py:3094-3099 — 孤儿 reap 与自动启动的「复用判定」互相竞态，可杀掉刚认领的 ASR 进程

**问题**：宿主启动时 reap 孤儿 audiocpp 与自动启动字幕服务的「复用判定」互相竞态：模型加载的几十秒里 8756 未监听，reap 判据 sub_port_open() 为假，可把 ensure_server 刚认领的 8083 孤儿进程杀掉——/health 仍报 ready 但所有转写 backend_unavailable，要等 5 分钟空闲回收+重拉才自愈。

**依据**：subtitle_auto_start 时 sub_start()（:3094-3095）拉起服务后立刻起 reap 线程（:3099）；reap 判据 `if sub_port_open(): return 0`（:1030-1031），而 uvicorn 先跑 lifespan.startup() 再绑端口（.venv uvicorn/server.py:107 实查）；此窗口内 ensure_server 的 `if self.probe(): 直接复用`（audiocpp_backend.py:196-201）先认领孤儿，reap 随后 netstat+taskkill（:1033-1035）杀之。两个组件对同一进程的所有权判定互相矛盾。

#### F06 [中][缺陷] host_server.py:1404-1421、1528-1529 — 下载中断把半截 .part 扶正为正式文件，整条下载链路无完整性校验

**问题**：下载中断会把半截 .part 直接 os.replace 成正式文件且无任何完整性校验，模型文件重试只查 size>0 即跳过——一次断流等于永久损坏的模型还显示「已安装」；整条下载链路（模型/llama 运行时/更新安装包）无哈希或签名校验。

**依据**：_download_once 读循环结束后未校验 done>=total 就 os.replace(part, dest)（:1418-1420）；原发现用本地截断 HTTP 服务实测：Content-Length=1000 只发 100 字节后断开，read 循环正常返回不抛异常。_model_dl_worker 对已存在文件 size>0 即 continue（:1528-1529），截断的 model.safetensors 永不重下；MODELS_CATALOG（:1237-1352）无 digest；llama 运行时 zip 解压后仅查 llama-server.exe 存在即被执行（:1504-1509）；更新安装包只比对 GitHub API 自报大小（:2133-2134）。原子性（.part+os.replace、206 校验）做得好，缺的是完整性校验。

### 前端（3 条）

#### F07 [高][缺陷] ui/app.js:1184-1215 — 更新下载失败后进度弹窗永久卡死，整个 UI 锁死到重启

**问题**：更新下载失败后进度弹窗永久卡死：progress 模式隐藏全部按钮、error 分支不隐藏弹窗、无背景点击/键盘关闭，全屏遮罩把整个 UI 锁死到重启应用。

**依据**：本次复核抽查证实：renderUpdate 仅在 downloading/available/ready 三态调 showUpdateModal（app.js:1192-1203），error 分支（:1188）只更新设置页文字；showUpdateModal 在 progress 模式把 updModalGo/updModalLater 都 hidden（:1210-1211），无 error 态隐藏弹窗路径。原发现补充：modal 无背景点击/键盘关闭（bind() 仅 1065-1075 两按钮可关），.modal-ov 为 position:fixed inset:0 z-index:90（ui/styles.css:740）拦截全部点击；下载失败是常见路径（host_server.py:2113 注释自述 GitHub 直连常被重置）且后端无取消接口（路由仅 check/download/install，host_server.py:2007-2011）。结果：下载中断一次，界面只剩停在中途的进度条，只能杀进程。

#### F08 [中][缺陷] ui/app.js:670-675、700-720、1283 — 模型下载完成触发表单重填，静默清掉用户未保存的输入

**问题**：翻译模型下载完成时 loadSubtitleConfig() 无条件重填整个字幕配置表单，静默清掉用户未保存的输入；用户没察觉就点保存会把旧值存回去（以为配好云端实际还是 local）；启动后 1 秒的首次 loadSubtitleConfig 同样无护栏。

**依据**：loadModels 的 done 分支直接 `S.localModels=null; loadSubtitleConfig()`（:670-675）；loadSubtitleConfig 对 #mtBackend/#mtModel/#mtBase/#mtCloudBase/#mtCloudModel 全是无检查赋值（:700-720）；「用户已开始改就不覆盖」的 S.subCfgDirty 只包住 boot 后 2.5s 补拉（:1287 的 `if (!S.subCfgDirty)`），没包住这条路径；保存提交所有字段当前值（:853-883）。修法：重填前检查 dirty/聚焦，或仅更新模型下拉选项。

#### F09 [中][缺陷] ui/app.js:772-782、821-826 — 媒体根目录增删基于客户端缓存全量回写，背靠背操作丢失更新

**问题**：媒体根目录增删都基于客户端缓存的 S.settings 全量回写，两个背靠背操作会丢失更新：删除 A → 1s 轮询带回仍含 A 的旧列表 → 添加 B 把 A 一起 POST 回去（刚删的目录复活），toast 报「已移除」但目录实际还在。

**依据**：addRoots 用 S.settings.dlna_roots 拷贝追加后全量 POST（:772-782），删除同样从缓存构造全量列表（:821-826）；S.settings 只靠 1s 轮询刷新（:248），服务器 ThreadingHTTPServer 并发处理（host_server.py:40、3074），GET /api/state 在删除 POST 落盘（save_settings tmp+os.replace，:475-486）前读到旧设置回填。修法：增删改为增量 API 或提交前带版本号/重新拉取。

### 字幕服务（11 条）

#### F10 [中][缺陷] server_app.py:631-637、644-647 — 在飞计数与空闲时钟两处竞态，空闲回收临界点掐断正在上传的首个请求

**问题**：/transcribe 的在飞计数与空闲时钟两处竞态：先读完请求体才 _INFLIGHT+1，空闲回收临界点恰逢首个请求上传时被 reaper os._exit 掐断（丢块+服务重启数十秒）；finally 里先减计数后刷 _LAST_REQ_TS，超长请求结束瞬间也可被抢杀。

**依据**：`body = await read_capped_body(...)`（:632）在 `_INFLIGHT += 1`（:636-637）之前；reaper（:151-175）两道栅栏只查 _INFLIGHT，注释（:145-148）声称的「最终检查与 os._exit 同锁」只覆盖已自增的请求；对照 /transcribe/stream 是先加计数再读体（:752-757），两入口口径不一致。暂停超过 idle_release_min 后恢复观看的首块音频正落窗口。另外 finally 先 `_INFLIGHT -= 1` 再 `_LAST_REQ_TS = time.time()`（:644-647），超长请求在减完计数未刷时钟的间隙会被判空闲退出。

**修法**：进 handler 第一时间自增（finally 递减），finally 先刷时钟再减计数。

#### F11 [中][缺陷] server_app.py:117-124、516-517、544-559、660-663 — 会话状态进程级全局单份，多设备并发串台且可被注入文本

**问题**：字幕会话状态是进程级全局单份（_HYBRID 混合缓冲、_LAST_CTX、stream_bridge 的 _recent_ja/_last_ctx），无客户端隔离：头显与手机都会直连 POST，两设备并发推流时音频交错进同一缓冲（两边字幕全乱、数据错误），_LAST_CTX 跨设备串台（热词/翻译上下文用错对白），配合默认无鉴权第二台设备可注入任意文本到下一句字幕与云端提示词。

**依据**：_get_hybrid_buffer 是进程级单例（:544-559），锁只护构造不护 feed（:573-574 直接 hbuf.feed）；_LAST_CTX 全局且 :661-662 将 prev['src'] 截断后作所有请求的 ASR 热词、:687-689 拼进云端提示词；stream_bridge.py:107-111 同样全局；hybrid_segmenter.py:18-19 注释自认「单客户端是既有事实」。全文件无 inflight 互斥或按来源（令牌/IP）区分机制。

#### F12 [中][缺陷] server_app.py:213-221、446；audiocpp_backend.py:550-557 — ASR 子进程意外退出后无任何请求路径自愈

**问题**：audiocpp_server.exe 运行中意外退出（崩溃/被杀）后无任何请求路径自愈：ensure_server 只在 lifespan 启动时调一次，之后转写失败只回错误类别，/health 的 asr_ready 判据与子进程死活无关恒报 True——头显持续推流、字幕静默全空。

**依据**：server_app._make_asr 里 be.ensure_server() 仅 lifespan 执行（:213-221）；请求路径 speech_spans 返回 None → transcribe 回 error=vad_failed（audiocpp_backend.py:550-557），单段 urlopen 失败只 append 带 error 的空段（:606-614），从不重试 probe/ensure_server；/health 的 asr_ready = backend_kind != "unavailable"（:446），而 backend_kind 是类属性 "audiocpp"（audiocpp_backend.py:78）。

## 三、AI 字幕服务专项分析

### 字幕链路

头显把 16k/s16le/单声道裸 PCM 块直接 POST 到 8756：非流式走 server_app.py:618 transcribe→_transcribe_impl(:650)；流式走 :748 transcribe_stream→stream_bridge.transcribe_stream(:219)。识别：asr.segmentation=hybrid 时经 _hybrid_transcribe→HybridBuffer.feed（hybrid_segmenter.py:102，RMS+VAD 切整句，未成句可回 partial 临时稿）；chunk 模式直接 AudioCppBackend.transcribe（audiocpp_backend.py:529）：speech_spans(:399) 调 audiocpp_cli.exe 做 silero VAD，段合并/8s 硬切后写临时 wav，POST 回环 8081 audiocpp_server.exe /v1/audio/transcriptions（模型 id qwen3-asr-stream，含上一句原文作热词，回显则无热词重试）。text_filters 过滤重复退化/拉丁幻觉并按 keep_segment 做重叠去重。翻译：translate_engine.Translator.translate_segments(:803) 批量 JSON+键校验纠错+免费兜底；local 后端由 llama_backend.LlamaBackend.ensure_server 拉起 llama-server.exe:8082（启动期 server_app 已预热）。最后 server_app 剥引号、块内碎片去重、_display_zh 隐藏未翻泄漏段，以视频绝对时间返回 segments（含 translation）JSON 或 SSE delta/done，并附 recommended_chunk_sec 档位建议。

### 专项发现展开（area=字幕服务，F10–F20 共 11 条）

**可用性与自愈（最影响观感）**

- **F12（ASR 无自愈）**：audiocpp_server.exe 只在 lifespan 启动时拉一次（server_app.py:213-221），运行中崩溃/被杀后没有请求路径会重拉——speech_spans 失败只回 vad_failed（audiocpp_backend.py:550-557），单段失败只 append 空段（:606-614），而 /health 的 asr_ready 判据是类属性恒 True（server_app.py:446）。结果：头显持续推流、字幕静默全空，宿主侧看不到任何异常。这是字幕链路里最典型「表面健康、实际死亡」的故障。
- **F10（空闲回收竞态）**：/transcribe 先读 100MB 上限的请求体再 _INFLIGHT+1（:632 vs :636-637），流式入口口径相反（:752-757）；finally 先减计数后刷时钟（:644-647）。空闲回收临界点恰逢恢复观看的首块上传时被 os._exit 掐断，丢一块+服务重启数十秒。
- **F18（墙钟计时）**：空闲计时用 time.time()（:162），同文件对 _LAST_PARTIAL_TS 已用 time.monotonic()（:113、:582）；时钟回拨/前跳会显存驻留或误杀在用服务，口径统一即可消除。

**并发与状态隔离**

- **F11（全局单份会话状态）**：_HYBRID 缓冲、_LAST_CTX、stream_bridge 的 _recent_ja/_last_ctx 都是进程级单例，锁只护构造不护 feed（:573-574）；hybrid_segmenter.py:18-19 注释自认单客户端假设。但 8756 绑 0.0.0.0 且头显与手机都会直连，两设备并发推流=音频交错+上下文串台+可注入文本。与 F16（无鉴权）叠加后是本链路最大的安全/正确性复合风险。

**配置与数据完整性**

- **F13（非原子配置写入→服务起不来）**：_recover_layout 用 shutil.copy2 直写现役配置（user_paths.py:296）、并发首启共用固定 tmp 名 .migrating（:234），可产生半截 JSON；坏 JSON 使 server_app.py:57 模块级 CFG 加载在 import 阶段即崩，宿主只报 code 1，UI 无修复路径。对照 integrated_settings 已有 refuse+backup（host_server.py:453-467），字幕配置应同级对待。

**功能正确性**

- **F14（流式不传 lang）**：/transcribe/stream 收 lang 但 _multipart 只发 model/stream/file（stream_bridge.py:173-182、:343）；离线路径同类问题修过并有注释教训（audiocpp_backend.py:48-51）。ja 恰好撞对上游默认、en 必错。
- **F20（hybrid 热词失效）**：asr_extra 算了不传（server_app.py:662 vs :665-668），_hybrid_transcribe 两处写死空串（:587、:599）；发运默认档位就是 hybrid，模块头注释列为核心设计的机制默认静默失效。

**资源与性能**

- **F15（断流连接泄漏）**：gen() 无 finally，GeneratorExit/CancelledError 不被 except Exception 捕获（stream_bridge.py:419-428）；断开后 resp.read1 占着线程池线程到 600s 固定超时（:346、:363-367），反复断流堆积死解码并抑制空闲回收。离线路径已按音频时长收紧超时（audiocpp_backend.py:596-600），流式未跟进。
- **F17（锁内 VAD 重跑）**：feed() 持锁 spawn audiocpp_cli.exe（hybrid_segmenter.py:111、:180-184），未切中即全缓冲重跑，hard 切句又丢弃 regions 重跑（server_app.py:603-606）；连续语音 3s→5s→7s+hard 切共 4 次 CLI spawn，约 20s 重复音频。

**安全**

- **F16（无鉴权+无过载防护）**：默认 auth_token=""（config.json:88）且全仓库无下发入口（docs/cross-repo-consistency.md:76 列为契约未实现）；100MB 体上限（:86）、无并发上限、无 Origin 栅栏（8790 有，host_server.py:1928-1936）。同网裸奔+浏览器 no-cors 可直达。
- **F19（信息泄露）**：/health 与 8791 /api/headset/status 泄漏绝对模型路径与异常全文，与自身 _error_kind 脱敏标准矛盾，定 low（已核实不含密钥）。

### 本段改进建议

1. **自愈闭环**：transcribe 两入口先 probe()（已有，2s 超时），失败且 _proc 已死时调 ensure_server 重拉一次（RLock 可重入）；/health 的 asr_ready 改为反映子进程真实死活（F12）。
2. **计数口径统一**：两入口都进 handler 第一时间 _INFLIGHT+1、finally 先刷 _LAST_REQ_TS 再减；空闲计时改 time.monotonic()（F10、F18）。
3. **断流兜底**：stream_bridge gen() 套 try/finally 关上游连接；超时按块时长收紧或加首字节/帧间空闲超时（F15）。
4. **多设备与鉴权**：默认生成随机 token 由宿主下发到 UI/设备、8756 补 Origin 栅栏、并发上限+recommended_chunk_sec 背压快速失败；会话状态按来源（令牌/IP）隔离或 inflight 互斥（F11、F16）。
5. **配置防坏与自恢复**：_recover_layout 改 tmp+os.replace、迁移 tmp 名加随机后缀；load_config 失败时改名隔离坏文件+从出厂模板重建+告警（F13）。
6. **正确性小修**：stream_bridge 透传 lang 与 asr_extra（上游 ensure_server 模型配置补 language 字段）（F14、F20）。
7. **VAD 提效**：VAD 移到锁外对拷贝计算、feed 间只评新增尾部、hard 切复用 feed 期 regions、长期换常驻 VAD 进程（F17）。
8. **翻译侧配套（area=翻译引擎，直接决定字幕体验）**：熔断加半开探测（F21）、空译文/解析失败归 alive 不计熔断（F22）、模型切换串行化/滞回+重验 _MT_WARM（F23）、逐句路径加预算与更短超时（F24）。

### 4.3 实测结论与相对盘点的修正
