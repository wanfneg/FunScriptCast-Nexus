# Win11 Live Captions（实时字幕）调研报告

> 调研日期：2026-10-02（R120）。方式：**本机实测**（Win11 build 26200 / RTX 4070 笔记本）+ 社区实现源码核对。
> 目的：评估"借 Windows 11 内置实时字幕，实现**词级浮现 + 低延迟**的中日字幕"这条路线——怎么调用、怎么接入 Nexus 体系、对素材/环境有什么要求。

---

## 0. 结论先行

1. **技术路径成立且干净**：用 **UI Automation（UIA）读取 `CaptionsTextBlock`**——不挪用模型、不改进程，社区同款（LiveCaptions-Translator 纯 UIA）。
   ⚠️ 另一主流开源实现 LunaTranslator 走的是 **LunaHook 注入进程**路线（灰区，Q&A 里"禁止挪用"针对的也是这类）——**不采用**。
2. **日语可用**：语言列表里"日语(日本)"**直接可选**（本机实测），无需装语言包、无需管理员。
3. **它是"逐词浮现"的**（实测时间线见 §3）：增量 1~5 字符、0.1~0.4s 一次，句末自动补句号、新句换行滚动——**正是用户想要的效果**。
4. **硬约束：系统输出必须有实际声音。** 系统静音时 Live Captions 听不到任何东西（实测踩坑两小时：静音期间 TTS/视频全无输出，开声后立刻出字）。
5. **对 Nexus 的接入价值分场景**：
   - **PC 播放（媒体库内置播放器）**：天然适配——声音从 PC 出 → Live Captions 直听 → 读词级文本 → **接我们的翻译管线**（Sakura/llama）→ 输出"中文、词级浮现"。这是本报告最推荐的落点。
   - **VR 头显播放（主场景）**：PC 无音频（头显侧解码），需"音频回灌虚拟声卡"方案才可用（复杂、依赖第三方驱动，见 §5 路线 B）——**建议优先做自研词级增强**（路线 C）。
6. **建议**：以 **POC（PC 播放场景接入）**立项验证体验，同时评估自研词级出字的成本——两者不冲突（翻译管线与头显协议共用）。

---

## 1. 背景与限制（为什么不能"直接调用"）

- **模型许可**：Live Captions 的识别模型（`livecaptionsbackend.dll` 等）**禁止挪用**——不能提取权重用于自建应用。
- **无公开 API**：微软**没有**给第三方提供调用 Live Captions 内部引擎的接口。
  - 文档里的 `Microsoft.Windows.AI.Speech` 是**另一套**设备端识别 API（与 Live Captions 模型/运行时分离），需要 MSIX 打包 + `systemAIModels` 能力声明（受限），且**不是** Live Captions 的引擎。
- **合法路径**：**读取用户可见的界面输出**（UIA/OCR/内存读取三类）。本报告只评估 **UIA**（干净、稳定、无注入）。

## 2. 本机实测记录（可复现）

### 2.1 环境与启动

| 项 | 结果 |
|---|---|
| 启动方式 | 直接运行 `C:\Windows\System32\LiveCaptions.exe`（无需 MSIX/商店） |
| 窗口 | 类名 `LiveCaptionsDesktopWindow`，名称"实时辅助字幕"，可置顶/隐藏（`SetWindowPos`/UIA） |
| 现有实例 | 检测到已有进程则复用（社区项目"先杀再起"的做法我们不取） |

### 2.2 UIA 元素清单（AutomationId）

| 元素 | aid | 用途 |
|---|---|---|
| 字幕文本容器 | **`CaptionsTextBlock`** | **读取入口**（`.Name` 即当前字幕全文） |
| 字幕滚动区 | `CaptionsScrollViewer` | 容器（含历史） |
| 设置按钮/菜单 | `SettingsButton` / `SettingsMenuFlyout` | 程序化控制 |
| **实时字幕语言** | **`SpeechModelDropDown`** | 语言切换（含"日语(日本)"） |
| 继续按钮 | `ContinueButton` | 语言选择面板确认 |
| 停止/关闭 | `CloseButton` | 生命周期控制 |
| 麦克风提示 | `MicrophoneErrorTip` | 状态观察 |

### 2.3 语言支持（实测）

- 下拉列表 17 项：简体/繁体中文、**日语(日本)**、朝鲜语、英/法/德/意/丹麦语等。
- **切换日语 = 一步点击**（`ListItemControl` 点击 → `ContinueButton` 确认），**无下载提示、无管理员**。

### 2.4 ⚠️ 关键环境约束（实测踩坑）

- **系统静音 ⇒ 完全无输出**：播放器在放、音量 30，但系统主音量静音 → Live Captions **什么都听不到**。
- 开声后**立刻正常出字**（用户实测确认）。
- 含义：**"系统音频"来源 = 实际输出电平**。若接入，需要在产品层处理（提示用户/或在播放时确保非静音；如需"静音看片"场景，得走虚拟声卡/回灌路线）。

## 3. 显示行为实测（核心数据）

### 3.1 词级形态（SIVR-001 日语对白段，两轮采样）

> 文本时间线（节选，完整见 R120 归档）：
>
> ```
> [22.6s] 教え
> [22.7s] +てあげる   → 教えてあげる
> [23.0s] +ね        → 教えてあげるね
> [23.4s] +。        → 教えてあげるね。
> [26.6s] +（\n）可愛 → 新句换行
> …
> [30.2s] +な → +んだ → +けど
> [32.2s] +（\n）かわ → +いい → +ですか
> ```

**结论**：
- **增量粒度**：1~5 字符（多数 1~2 字符，偶有短语块如"ってあげる""しょうがね"）。
- **增量间隔**：0.1~0.4s（说话活跃期）；**句间有 3~6s 静默空窗**（跟随说话节奏）。
- **标点**：句末自动补"。"；**新句以 `\n` 换行**。
- **UIA 里是累积全文**（会持续增长到十几行）——**接入时需自己"取尾部 N 行/增量 diff"**（如同秒内 diff 出新增段）。
- **识别质量**：与 SIVR-001.srt 语意逐句吻合（"ライブの衣装なんだけど…かわいいですか" ↔ "这件演出服呢／可爱吗？"）。
- **出首块延迟**：约 0.5~2s（未精确量化；从"说话开始"到首个增量出现）。

### 3.2 与 Nexus 现管线的对比

| 维度 | Nexus 现管线 | Live Captions 路线 |
|---|---|---|
| 出字形态 | **整句**（混合切句器定界） | **词级增量**（1~5 字符/0.1~0.4s） |
| 识别延迟 | 句尾定界 + ASR 块处理 | 首块 ~0.5~2s |
| 翻译 | Sakura/llama（本地） | （原文由 LC 给）翻译仍走我们的管线 |
| 素材依赖 | 任意（音频推流） | **系统输出有声**（PC 播放场景成立） |
| 模型许可 | 自研（合规） | 读 UI 输出（合规）；**注入方式不做** |

## 5. 接入设计（三路线）

### 路线 A：PC 播放场景直用（推荐 POC）

```
媒体库播放（WebView 出声）
  → Live Captions（日语，程序化启动+切语言+隐藏窗口）
  → UIA 轮询 CaptionsTextBlock（~100ms）→ diff 出新增片段
  → 新增片段送 Nexus 翻译管线（现有 llama-server/Sakura，含缓存）
  → 组装成 partial/final 事件 → 头显（沿用现有字幕协议）
```
- 优点：**全部使用现有基础设施**（翻译管线、头显协议、宿主进程内可跑 UIA/COM）；不碰识别模型。
- 约束：要求系统输出有声（静音场景提示用户）；LC 启动/语言切换状态机要健壮（掉线重拉）。
- 工作量估计：中（宿主侧一个"LC 抓取器"+ 与字幕协议的 partial 字段对接）。

### 路线 B：VR 头显场景（音频回灌）

```
头显 PCM 推流（现有 8756 通路）
  → PC 端虚拟声卡播放（VB-CABLE 等第三方驱动）
  → Live Captions 听"系统音频"
  → 同路线 A 的后半段
```
- 优点：与现有推流链路复用。
- 缺点：**依赖第三方虚拟声卡**（安装/许可/兼容性），且"回灌"多一层；延迟叠加。**不推荐**——VR 场景不如直接做路线 C。

### 路线 C：自研词级出字（不依赖 LC）

- 现有基础：管线已支持 **partial 渐进出字**（头显端协议有字段）；`audiocpp` 有流式接口能力（`stream_bridge`）。
- 内容：把"整句定稿"改为"**流式 partial + 词级 diff 推送**"，效果对齐 Live Captions 的观感。
- 优点：**全平台生效**（PC/头显/手机一致）、无系统/素材约束、无"静音"坑。
- 缺点：需要 ASR 真流式（当前混合切句是"句级"）；延迟与准确率需实测调优。
- 工作量估计：中~大（涉及识别侧改造与评测）。

## 6. 建议与待拍板

1. **立 POC：路线 A 最小验证**（PC 播放 → LC 抓词级 → 翻译 → 头显）——用 SIVR-001 做端到端观感测试；成本低、能立刻看到"词级中日字幕"的体验上限。
2. **并行评估路线 C 的工程量**（现有流式能力盘点 + 一次对比评测）——若两者接近，**长期应走自研**（无环境依赖）。
3. 待拍板：①是否立 A 的 POC；②LC 的"静音约束"是否可接受（产品文案/行为）；③日语语言包/LC 的系统要求是否纳入安装引导（Win11 22H2+；日语直接可选，无需装包——已实测）。
