# 字幕链路审查与架构评估（2026-10-17）

> 环境：D 盘安装版 v1.0.91（`D:\FunScriptCast-Nexus`），宿主 PID 32716，字幕服务当前 **stopped**。
> 方法：逐行读代码 + 在本机跑可复现的最小验证 + 实测接口/进程/Windows 行为。
> 标注：**实测** = 本机跑出来的数字；**静态推断** = 只读代码推出、未做端到端复现。

---

## 一、结论

1. **最严重的 bug 是 `lc_capture.start()` 的自锁死锁**（`vendor/player/lc_capture.py:76-78` 与 `:108`）。用户重复点同一个语言、或从日语切英语，`/api/lc/start` 就会永久挂起；连带 `/api/lc/state` 也拿不到锁，前端 300ms 轮询开始无限堆积。**已实测复现**。
2. **第二严重的是"字幕开着但一直不出字"的静默失败**：字幕服务一旦被停（今天日志里发生了两次），llama-server 随 Job Object 一起死，但 LC 抓取器仍报 `running=True / lc_ok=True / error=''`，前端完全无法感知，屏幕就是空白。
3. **用户能直接看到的另一个 bug 是字幕闪烁**：每句新定稿时译文还没回来，前端无条件把 DOM 清空，形成 1–3 秒空白。
4. **架构不需要换。** 实测下来，没有一项延迟是"架构选错了"造成的——全部是具体实现问题：同步阻塞探测、Windows 回环 connect 用满超时、UIA 路径写错、前端轮询无节流。换成 Electron/Tauri/Rust 一行代码都不会让这些变好。

## 二、已证实的缺陷

### 高

#### H1. `start()` 持锁调 `state()`，非重入锁自锁 → 永久死锁

- **位置**：`vendor/player/lc_capture.py:76-78`、`:108`
- **现象**：用户重复点「日语」（已是日语）、或运行中切「英语」→ `/api/lc/start` 的 HTTP 请求永不返回；随后 `/api/lc/state` 也永久阻塞。
- **根因**：
  ```python
  with self._lock:                     # :76
      if self._running and self._cur_lang == want:
          return self.state()          # :78 ← state() 内部也要 with self._lock
  ...
      return self.state()              # :108 同样在 with self._lock 块内
  ```
  `threading.Lock()` 不可重入，同一线程第二次 acquire 永久阻塞。
- **实测**：伪造 `_running=True, _cur_lang=日语` 后调 `start("ja")`，2 秒不返回；再调 `state()`，2 秒不返回。
- **影响链**：HTTP 线程永久占用 → 前端 300ms 轮询（每次也调 `state()`）全部堆积 → 宿主线程数持续增长。
- **修复**：把 `state()` 调用移到 `with self._lock` 块**外**；或改用 `threading.RLock()`。两处都要改。

#### H2. 字幕服务停止后，LC 静默失败，用户只看到空白

- **位置**：`host_server.py:1223`（`sub_stop` 的 `taskkill /T`）、`vendor/subtitle/llama_backend.py:219`（Job Object）、`vendor/player/lc_capture.py:451-455`（翻译失败置空不重试）、`ui/app.js:1647-1661`（只在预热期检查 error）
- **现象**：AI 字幕开关是开的、状态显示正常，但屏幕上永远没有字幕。
- **根因链**：
  1. 用户点「停止字幕服务」或设置页保存触发重启 → `sub_stop()` → `taskkill /T` 杀整棵进程树；
  2. llama-server 挂在字幕服务的 Job Object 下，一起死；
  3. `lc_capture` 的抓取线程**不知道**，仍 `running=True / lc_ok=True / _err=''`；
  4. 每句定稿 → `_lc_translate` → `POST :8756/translate/text` → 连接拒绝；
  5. 异常被 `except` 捕获，`zh=''`，只写一行日志（日志在宿主内存，UI 看不到）；
  6. 前端拿到 `lines[-1].zh=''` → 不渲染 → 空白；
  7. `lcWarming` 已结束，`lcPoll` 不再检查 `lc.error` → 永远无法发现。
- **实测证据（今天 D 盘日志 + 事件流）**：
  ```
  11:22:43  拉流 → 触发字幕服务预启动（SIVR-001.mkv）
  11:22:44  事件流：字幕服务已启动
  11:30:21  事件流：字幕服务已停止 · 模型内存已释放
  11:46:54  拉流 → 字幕服务已启动
  11:58:37  字幕服务已停止 · 模型内存已释放
  ```
  `lccapture` 模式已禁用空闲回收（`server_app.py:235` 的 `continue`），所以这两次停止只可能来自 `sub_stop()`（用户点停止/设置保存/退出），不是自动回收。
- **修复**：
  - `_lc_translate` 失败时把错误写进抓取器状态（新增 `_mt_err` 字段），`/api/lc/state` 透传；
  - 前端在 `lcWarming=False` 后也消费 `error`/`mt_ok`，字幕层显示「翻译服务已断开，点此重启」；
  - 抓取器检测到连续 N 句翻译失败时自动 `sub_start()` 一次（或至少上报）。

#### H3. 前端字幕空窗闪烁（1–3 秒空白）

- **位置**：`ui/app.js:1700-1704`
- **现象**：每句字幕之间屏幕闪一下空白。
- **根因**：
  ```js
  box.innerHTML = last.zh
    ? '<div class="lc-line">' + esc(last.zh) + "</div>"
    : "";                                   // ← zh 为空时无条件清空
  ```
  句子 B 定稿时 `zh` 还是空串（翻译 worker 要 1–3 秒），key 因 `ts` 变化而改变 → 进入渲染分支 → 清空 DOM。
- **修复**：`zh` 为空时**不要动 DOM**（保留上一条），等译文回来再替换。一行改动。

### 中

#### M1. LC 语言检查每次固定多等 5.9 秒（实测）

- **位置**：`vendor/player/lc_capture.py:240-307`
- **根因**：代码只认 `SpeechModelDropDown` 判断当前语言。但**实测 LC 就绪态根本没有这个控件**（15 秒观察窗内始终 `Exists=False`），就绪态只有：
  ```
  TextControl aid=ReadyToCaptionTextBlock name='已准备好在 日语(日本) 中显示实时字幕'
  ButtonControl aid=SettingsButton name='设置'
  ```
  → 每次启动都判定"语言未设置"，走完整切换流程。
- **实测耗时**（完整走一遍）：
  | 步骤 | 耗时 |
  |---|---|
  | `combo.Exists(1)` 不存在 | 1.02s |
  | Invoke 设置 → sleep | 0.8s |
  | 找 `ChangeLanguageMenuFlyoutItem` | 存在 |
  | Invoke → sleep | 1.5s |
  | `combo.Exists(1)` 出现 | — |
  | Expand → sleep | 1.8s |
  | 遍历找日语项 → Select → sleep | 1.2s |
  | **合计** | **5.9s** |
- **影响**：用户每次开 AI 字幕，视频要暂停多等这 5.9 秒。
- **修复**：先读 `ReadyToCaptionTextBlock`，用正则取出语言名，已等于目标就直接 `return`（0 秒）；只有不匹配时才走设置菜单。

#### M2. `/api/lc/state` 恒慢 1029ms

- **位置**：`host_server.py:2436-2439` → `_lc_mt_ok()` `:4119-4129` → `sub_health()` `:770-776`
- **实测**：连续三次都是 1029ms，响应只有 172 B。
- **根因**：`sub_health()` 用 `urlopen(timeout=1.0)` 且**无缓存**。Windows 回环 connect 到未监听端口不会立刻 RST，而是用满超时（实测 `timeout=0.4→405ms`、`1.0→1013ms`）。字幕服务没跑时每次都吃满 1 秒。
- **连带**：前端 `lcPoll` 300ms 一次 × 1029ms = 同时在飞约 3.4 个请求，持续堆积。
- **修复**：
  - `sub_health` 加 2 秒缓存（失败也缓存，与 `sub_translate_stats` 同款）；
  - 或 `_lc_mt_ok` 直接读 `sub_state()` 里已缓存的 health，不要单独再探一次；
  - 前端 `lcPoll` 加 in-flight 标志（上一发未回不发下一发）。

#### M3. `/api/state` 每 2 秒卡 1 秒

- **位置**：`host_server.py:2148` → `sub_translate_stats()` `:782-795`
- **实测**：`60ms / 1029ms / 1038ms / 4ms / 1025ms` 交替。
- **根因**：`sub_translate_stats` 的 2s 缓存**失败也缓存**，但每次失效后仍对已停止的服务付 1 秒超时；`sub_state()` 里 `sub_port_open(0.4)` 同理。两者叠加约 1.4 秒（实测 1.03 秒，因为部分路径被缓存跳过）。
- **修复**：服务状态为 `stopped` 时直接跳过这两个探测（`sub_state()["status"] != "ready"` 就不问 `/translate/stats`）；或把失败缓存延长到 10 秒。

#### M4. LC 文本滚动导致整段重复定稿（静态推断，未端到端复现）

- **位置**：`vendor/player/lc_capture.py:385-413`
- **根因**：`CaptionsTextBlock` 是累积全文，但会滚动裁掉最早的行。裁掉后 `txt.startswith(committed)` 为假 → `committed=""` → 整段历史被当成新文本重新扫描定稿。
- **推演**（用真实切句逻辑）：
  ```
  屏1 "Aです。\nBです。\nCです。"  → 定稿 A, B
  屏2 "Bです。\nCです。\nDです。"  → 定稿 B, C   ← B 重复
  结果: [A, B, B, C]
  ```
- **修复**：改用**行级滚动窗口**——维护最近 N 行的去重集合，或按"最后一行索引 + 文本"做锚点对齐，而不是整体前缀比较。
- **未做的验证**：需要 LC 实际出声才能看到滚动，本次没跑（系统静音时 LC 完全无输出）。

#### M5. UIA 僵尸化自愈比设计慢 4 倍

- **位置**：`vendor/player/lc_capture.py:358-372`
- **根因**：`POLL_SEC=0.12`，但 `_read()` 里 `Exists(0.1)` 在元素不存在时**实际耗 430–460ms**（实测 20 次 8.8 秒）。所以 `alive_check >= 50` 名义 6 秒，实际 23 秒。
- **修复**：把 `Exists(0.1)` 换成 `Exists(0)`（不等待）或先查窗口再查元素；僵尸化检测改用时间戳而不是轮数。

#### M6. 启动竞态：抓取线程先起、翻译队列后建

- **位置**：`vendor/player/lc_capture.py:100-103`
- **根因**：`:100-102` 启动 `_run` 线程，`:103` 才 `self._tq = queue.Queue()`。若抓取线程在这几微秒内定稿一句，`_commit` 读到 `self._tq` 为 `None`（首次）或旧队列，该句永远没有译文。
- **修复**：把 `self._tq = queue.Queue()` 移到线程 `start()` 之前。

#### M7. 双翻译 worker 与"保序"承诺矛盾

- **位置**：`vendor/player/lc_capture.py:104-107`（两个 worker）vs `:444`（docstring 说"串行消费保序"）
- **实际影响**：前端只渲染 `lines[-1]`，所以乱序**不会**闪回旧句；但句密时（1–2 秒一句）先定稿的句子译文回来时已被后一句覆盖，用户感知为"漏句"。
- **修复**：要么改回单 worker（保序），要么前端改成"按 ts 顺序队列显示"而不是只看最后一条。

### 低（未复核，供参考）

- `stop()` 不清 `_lc_ok`（`lc_capture.py:117-118`），停止后 `state()` 仍报 `lc_ok=True`。
- 翻译 worker 在 `stop()` 时不 join，字幕服务已死时会滞留最多 60 秒（`_lc_translate` timeout）。
- `_ensure_language` 每次启动都会 `GetRootControl().GetChildren()` 遍历桌面（实测 0.4 秒，窗口多时 10 秒）。

## 三、架构性能评估

### verdict

**瓶颈不在架构，在实现。** 逐项归因后，没有一项延迟能靠"换技术栈"消除：

| 环节 | 实测 | 根因 | 换架构能否解决 |
|---|---|---|---|
| LC 语言检查（固定） | 5900 ms | UIA 路径设计错误 | 否，改代码 |
| 翻译单句生成 | 1500 ms | 模型推理 | 否，换模型才行 |
| `/api/lc/state` 响应 | 1029 ms | 同步探测 + Windows connect 超时 | 否，改代码 |
| `/api/state` 周期卡顿 | 1000 ms | 同步探测无失败缓存 | 否，改代码 |
| LC 未运行时 UIA 轮询 | 462 ms | `Exists` 超时用满 | 否，改代码 |
| HTTP 建连开销 | ~3 ms | HTTP/1.0 无 keep-alive | 否，改一行 |
| UIA 正常轮询 | 17 ms | — | 已可接受 |

### bottlenecks

1. **同步阻塞探测（最影响观感）**：`sub_health` / `sub_translate_stats` / `sub_port_open` 都是同步 HTTP，在服务未运行时每次吃满 1 秒。宿主是 `ThreadingHTTPServer`，每请求一线程，所以不会互相阻塞，但**每个请求本身**变慢 1 秒。实测 20 并发时线程峰值 33——没有崩，但完全是浪费。
2. **前端轮询没有节流**：`lcPoll` 300ms + 预热期 Worker 500ms，叠加约 5.3 QPS；单次 1 秒 → 持续 3–5 个在飞请求。
3. **LC 启动路径的固定等待**：语言检查 5.9 秒 + `win.Exists(20)` 最长 20 秒，全部在视频暂停期间。
4. **翻译链路的每句固定往返**：`_chat_local` 每句都 `ensure_server() → probe()`，每句至少 2 次 HTTP 到 llama-server。单次 RTT 只有 1–3ms，相对 1.5 秒生成可忽略，但属于可省的开销。
5. **VR 路径的 VAD 子进程**：每块起一次 `audiocpp_cli.exe`，实测 2 秒音频 0.19 秒、14 秒音频 0.5 秒。2 秒块下约占 10% 实时预算，可接受但不是零成本。

### options

**A. 定点优化（推荐）**
- 改动范围：`lc_capture.py`（死锁、语言检查、队列、滚动去重）、`host_server.py`（探测缓存、状态透传）、`ui/app.js`（闪烁、in-flight、error 消费）
- 工期：1–2 人日
- 收益：消除死锁与静默失败；开字幕等待从 5.9 秒降到 ~0 秒；API 卡顿从 1 秒降到 <20ms；闪烁消失
- 风险：低（都是局部改动，有单测）
- 打包影响：无

**B. 局部重构**
- 改动范围：把 LC 抓取并入字幕服务进程（省掉宿主↔服务的翻译 HTTP 往返）；宿主 API 改 `aiohttp`/`uvicorn` 异步
- 工期：5–8 人日
- 收益：翻译链路少一跳（约 1–3ms/句，可忽略）；异步后探测不占线程
- 风险：中（进程模型变更，打包/安装链路要重验）
- 结论：**收益远小于成本**，不建议

**C. 整体换栈（Electron/Tauri + Rust/Go 后端）**
- 工期：30+ 人日
- 收益：内存/启动时间改善，但**字幕延迟一个都不会变好**（瓶颈在 UIA、模型推理、Windows connect）
- 风险：极高（打包、签名、更新、安装链路全部重做）
- 结论：**不做**

### recommendation

**不转架构，走 A。** 先做三件事（按顺序）：

1. **修死锁**（H1）——这是唯一会让功能彻底卡死的 bug，两处 `return self.state()` 移出锁块。
2. **修静默失败**（H2）——把翻译错误透传到 `/api/lc/state`，前端消费；这是用户"字幕坏了"的主因。
3. **修语言检查**（M1）——先读 `ReadyToCaptionTextBlock`，省掉每次 5.9 秒。

### doNotDo

- **不要为了"性能"把宿主 HTTP 换成异步框架**：实测 `/api/settings` 只要 2–15ms，序列化 <1ms，问题在探测不在框架。
- **不要为了"延迟"换掉 Sakura-1.5B**：R98 已评测过 1.7B 更慢且显存代价高；延迟大头是句边界等待，不是模型速度。
- **不要给 LC 加虚拟声卡**：PC 场景不需要（R120.2 用户已定调）。
- **不要重写前端**：闪烁是 5 行代码的问题。
